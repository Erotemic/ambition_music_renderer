IMPORTANT: Never add tests for a specific song. Test the renderer, not the content. If a feature does not have a natural test, then don't add the test. Don't add a bullshit test for the sake of adding a test.

## Sampled-instrument authoring contract

- `ambition_music_renderer/data/instrument_catalog.yaml` is the checked-in authority for sampled instruments Ambition expects composers and agents to be able to use.
- The normal `download_ambition_audio_tools.sh` environment is expected to provide every catalog instrument. If a catalog ref does not resolve on the current machine, treat that as an environment/install problem rather than avoiding the instrument in authored music.
- Prefer stable MusicIR `instrument_backend: {kind: sfz, library_ref: ...}` identities from the catalog. Do not copy absolute `/data/audio-tools` paths or ordinary filename-selection `prefer` heuristics into scores when the catalog already owns them.
- A score-level `prefer` or explicit `sfz` is an intentional realization override, not normal boilerplate.
- `ambition_music_renderer/data/audio_environment_snapshot.json` is the checked-in observation of what the maintainer workstation was actually seen to contain. It is source-readable with no dependencies (`python -S dev/read_audio_environment_snapshot.py ...`). Use it when a remote agent needs disk/environment knowledge it cannot observe itself. It is observational; `instrument_catalog.yaml` remains the expected authoring contract.
- `SFZ_USAGE_CENSUS.json` and other files under `AMBITION_AUDIO_TOOLS_ROOT` are richer live-machine evidence. They provide exact paths, ranges, controllers, keyswitches, and health information when available; they do not define the supported authoring vocabulary.
- Use `python -m ambition_music_renderer instruments list` and `instruments describe <library_ref>` to discover the source-controlled vocabulary and known patch-level controls. Use `instruments doctor` on a machine with audio tools to compare expected downloaded sources and resolved roles against that contract.
- Instrument-backend compatibility spellings and resolution semantics belong in `instrument_resolution.py`. Renderers, audits, inspectors, caches, and validators should consume its canonical plan instead of interpreting `library_ref`, `sfz`, `prefer`, roots, or fallback fields independently.

## MusicIR compilation contract

- Existing MusicIR v1/v2 scores are durable regeneration inputs, not migration backlog. Never make v3 adoption depend on converting them. Preserve their compilation/render paths; a polished replacement should normally be a new v3 composition while the original remains regenerable.
- `docs/architecture_roadmap.md` is the campaign recovery document. Read it before cross-cutting MusicIR/instrument/generator/render-interchange work and update it when an architectural authority or roadmap decision changes.
- `ambition_music_renderer/data/generator_catalog.json` is the public v3 generator authority. The v3 compiler and introspection surfaces consume it. It owns public parameter types/ranges/enums and capability metadata as well as names/examples. A source-only agent can inspect it directly or run `python -S dev/read_generator_catalog.py ...`. Do not maintain a second public generator-name/parameter table in code or docs.
- `ambition_music_renderer/data/technique_catalog.json` is the backend-independent v3 articulation/technique vocabulary. Technique meaning belongs there; instrument-specific keyswitch/controller/alternate-patch realization belongs in instrument knowledge/resolution.
- `ambition_music_renderer/data/instrument_family_profiles.json` and derived `instrument_authoring_index.json` provide source-only composition guidance and canonical audition knowledge. Family guidance is conservative; do not invent patch-specific facts without census/smoke/listening evidence.
- `python -S dev/music_authoring_reference.py ...` is the combined source-only discovery surface for instruments, generators, processors, and techniques. It must work with only the standard library.
- `ambition_music_renderer.musicir.compile.compile_score()` is the canonical boundary between authored MusicIR and renderer consumers. New renderer, audit, inspector, cache, timeline, or export code should consume `CompiledScore` instead of calling a schema-specific compiler or reading semantic data from private `PrettyMIDI` attributes.
- MusicIR v1 and v2 remain supported compatibility frontends. MusicIR v3 is the authoring-graph direction: exact clips, reusable material, and procedural generator clips can coexist in one score before compiling to the same `CompiledScore`. Do not mass-convert existing cues merely to change schema labels.
- V3 score/part/voice/clip ids are source/interchange identity, not musical parameters. Source-only renames must not change compiled music or default generator randomization. Preserve `event_id` / `source_ref` provenance through compilation without making it part of the audio-semantic fingerprint.
- V3 generators must reuse the established layer implementations through the registered bridge until a generator is intentionally migrated to a clock-domain implementation. Do not copy an arpeggiator, guitar performer, drum pattern engine, etc. into a second v3-specific implementation.
- `musicir/normalize.py` owns source-schema compatibility and authoring aliases. Keep compatibility behavior there during migration; downstream code should see canonical schema/fields.
- `render.score_layers.build_score()` and `_ambition_note_events` / `_ambition_instrument_specs` / `_ambition_exact_score` are compatibility surfaces only. Do not add new dependencies on them.
- Preserve musical behavior while migrating. Generic migration-contract tests should compare expanded notes, velocities, timing, controllers, pitch bends, groups, section boundaries, MIDI resolution, and exact-score clock metadata. Audio-path changes should also have a deterministic generic render comparison when a dependency-free backend can exercise them.
- Do not add snapshots for named cues. Frozen migration fixtures must describe renderer capabilities generically so score edits remain free to evolve.
- `cue validate <cue>` compiles without synthesis and reports schema normalization plus the `CompiledScore` fingerprint. For v3 it also reports the authoring-graph fingerprint and clip/generator counts. The compiled fingerprint represents the synthesis/form contract, not source ids or a local sample-file realization.
- V3 source diagnostics belong in `validation/v3.py` and should use `validation/diagnostics.py` for stable code/path/location formatting. Catch source-shape/reference mistakes there when they can be explained without duplicating compilation. Leave lowering-only semantics to `compile_score()` and wrap those failures rather than reimplementing the compiler in validation.
- `cue graph`, `cue expand`, and `cue trace_event` are the canonical derivation-inspection surfaces. They consume `NormalizedScoreGraph`, `CompiledScore`, and `InstrumentResolutionPlan`. Do not create a debug-only note generator, harmony resolver, or sample resolver. For unfamiliar v3 behavior, inspect these surfaces before reading lower-level generator code.
- DAW interchange uses exact MIDI as editable transport and the `.musicir-interchange.json` sidecar as the provenance baseline. Reverse reconciliation is now active: `musicir.interchange_reconcile` classifies edited MIDI and applies supported edits by lowering only affected v3 clips. Keep MusicIR authoritative. Ardour is the primary DAW target and REAPER secondary; DAW-specific session adapters sit outside the neutral reconciliation core.
- During this migration, legacy compatibility paths stay in place until tests demonstrate their consumers have moved. Remove them in a later explicit cleanup rather than opportunistically while refactoring another subsystem.
- `dev/check_legacy_regeneration.py` is the permanent whole-corpus regeneration smoke gate: every committed v1/v2/implicit-v1 score must continue to compile. Do not add per-song fingerprint snapshots; for broad compiler refactors, generate ephemeral pre/post reports from the old and new trees and compare them together with the generic frozen migration contracts.
- New composition should start in v3 (`cue new` or `python -S dev/new_musicir_v3.py`). Use `cue quality` and `cue determinism` as evidence during iteration; quality diagnostics do not replace listening or define musical taste.

## Processing/mastering contract

- `ambition_music_renderer/data/processing_catalog.json` is the checked-in public authority for render-time processor names, aliases, parameter metadata/defaults, backend family, automation capability, and inspector templates. Source-only agents can read it directly or run `python -S dev/read_processing_catalog.py ...`.
- New v3 music should prefer the explicit top-level `processing:` block. `processing.stems`, `processing.groups.<name>`, `processing.sections.<id>`, and `processing.master` compile to `ProcessingPlan` objects. Do not add another renderer-specific interpretation of those chains.
- `processing.pipeline.apply_processing_plan()` is the execution boundary. Historical `postprocess`, `stem_postprocess`, `group_postprocess`, and `sections[].postprocess` remain supported through `processing.legacy`; they are compatibility inputs needed to regenerate v1/v2 assets.
- New v3 adaptive music defaults to one `composition_master`: optional canonical section-bus processing runs before the master, then full-section assets are slices of the mastered timeline. V1/v2 without an explicit policy retain historical `legacy_section_postprocess` behavior.
- `global_master_slices` and `section_postprocess` are accepted historical policy spellings. Internally use `composition_master` and `legacy_section_postprocess`.
- Processing changes that can affect old audio need generic PCM migration evidence. Do not change a historical flat-postprocess default as part of an unrelated refactor.
- `processing plan <cue>` is the inspection surface for normalized stage plans and mastering policy. `docs/processing_architecture.md` is the detailed signal-flow reference.

## Render dependency/currentness contract

- `ambition_music_renderer.render.dependencies` is the authority for the static inputs that determine rendered audio. Versioned generated paths, manifests, cue currentness, and stem caching should derive machine/resource identity from that layer instead of inventing another hash.
- `RENDERER_VERSION` is compatibility/history metadata, not a cache-invalidation responsibility. Do not bump a magic version just to make a renderer code edit take effect; production source/data are fingerprinted automatically.
- Fingerprint the narrow dependency actually used by a cue: resolved SFZ/include/sample files, selected SoundFont, plugin bundle, processor/model file, executable, etc. Do not hash all of `/data/audio-tools` or a whole plugin root as a shortcut.
- When adding a synthesis/processing backend whose output depends on a new machine resource, add that dependency to `render.dependencies` and a generic invalidation/locality test in the same change.
- `cue fingerprint <cue> --json` is the diagnostic surface for explaining current render identity. `audit instrument_drift` may describe historical changes but must not become a second currentness authority.
- Preserve the old `needs_render()` / `build_score()` interception points while their migration tests exist. New canonical checks may complement those hooks but should not bypass them until an explicit removal change updates the contract.
